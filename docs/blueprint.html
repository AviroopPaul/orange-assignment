Errand Agent Blueprint

The stack is FastAPI, PostgreSQL, Redis, Google ADK, Gemini and React, and one Docker Compose command runs it all. PostgreSQL holds all truth. Redis moves work between processes. The model can only read and propose.

Checked on 2 Nov 2026 with throwaway tests on real PostgreSQL 17 and Redis 8 containers and live Gemini. The full Compose stack does not exist yet, so make up is untested. Limits and budgets on this page are proposals.

Architecture

The core rule: the model can read and propose. Only deterministic code can change a booking, and only after a user approval that the model cannot produce.

Our deterministic code Untrusted model output Container or framework Storage Mock provider
  • Model tools: search_providers, get_provider, list_bookings, get_booking_status, update_request, propose_booking, propose_cancel, propose_reschedule, propose_memory.
  • Code-only tools: hold_slot (called inside propose_booking), book, cancel, reschedule.
  • Single agent: Guardrails live in code, so more agents would add model calls and cost without adding safety.
  • Scale path: api and worker hold no state, so --scale worker=3 works. scheduler stays at one copy. Database and Redis URLs come from the environment, so managed services can replace the containers later.

Commands

  • make up: Build, start, wait until healthy, print the URL.
  • make evals: Run all scenarios offline and write the eval table.
  • make logs and make down: Follow logs, or stop and keep data.
  • make reset: Delete volumes and reseed.
  • Compatibility: make uses docker compose, or docker-compose if the plugin is missing.

Build rules

  • One Python image: api, worker, scheduler, migrate, mock-provider and evals share it with different commands. Multi-stage build, uv.lock, non-root user.
  • Secrets: GOOGLE_API_KEY comes from the environment at run time and is never in an image or in git. .env.example lists all settings.
  • No key: The stack still starts. Chat replies clearly that no key is set.
  • Memory limits: Each service has one, because this stack must run on an 8 GB laptop with a 3.8 GB Docker VM. Lightly used after the tests, PostgreSQL took 34 MiB and Redis 12 MiB. I will set the others after measuring them.
  • Output: Traces and eval results go to bind mounts under ./artifacts and ./evals.

Redis rules

With a queue, a job can be lost or delivered twice. Booking code must stay correct in both cases, so PostgreSQL decides what is true and Redis only carries work.

UseHowIf Redis fails
Job streamRedisStreamBroker gives at-least-once delivery. Idle timeout is 60 s, longer than the 45 s saga limit, or a running job gets a second delivery. The library default of 10 minutes equals the hold lifetime, so it is too long.Jobs wait in the outbox table. The publisher resends them when Redis returns.
Pub/subWorker tells api about a notification, and api pushes it through SSE. Notifications are stored in PostgreSQL first, so a reconnect replays them with Last-Event-ID.Live push stops. Stored notifications appear on the next load.
Turn lockOne lock per session with an owner token and a 150 s expiry, longer than the 120 s run limit. It stops two turns from colliding. StaleSessionError is the backstop if a lock ever expires early.Chat fails closed with a clear reply. No tool runs.
  • Outbox: A domain change and its job row commit in one PostgreSQL transaction. A publisher then moves the row to Redis. This closes the gap where a crash between commit and enqueue would lose a job.
  • Every job is safe to repeat: The saga claims its attempt with a conditional update and a lease. A second delivery finds it claimed or finished. The idempotency key protects the provider call itself.
  • Sweeps: Every 15 s, the scheduler enqueues a sweep job. It looks in PostgreSQL for unpublished outbox rows and attempts with expired leases, and requeues them. So recovery from a killed worker or a full Redis wipe needs nothing from the broker. A lost booking attempt is picked up about 75 s after the worker dies, well inside the 10-minute hold.
  • Broker settings: Set unacknowledged_lock_timeout. The default is no expiry, so from reading the code, a worker that dies holding that lock could block reclaim. I have not tested this case.

What I tested on real containers

QuestionResultEffect on the design
Does a killed worker's job come back by itself?Only when a new job arrivesWith a 5 s idle timeout, the job was still undelivered after 40 s on a quiet queue. One new job brought it back in 0.1 s. The reclaim code runs only after a read that returned new messages. This is why recovery rests on PostgreSQL sweeps.
Can a job run twice while still running?YesA 14 s job on a live worker, with a 5 s idle timeout, got a second delivery when a new job arrived. So idle timeout must exceed the job limit, and the saga needs its lease and idempotency key.
Does wiping Redis lose a queued job?YesThe job never ran. This is why the outbox exists.
Can two callers consume one approval?NoOf 10 concurrent conditional updates on separate connections, exactly 1 won.
Does the index stop duplicate bookings?YesThe partial unique index rejected a second active booking, and allowed a new one after cancel.

The ADK decision

Use ADK, pinned to 2.13.0, and keep it thin. The gateway, saga and memory code do not import ADK, so we can replace it later at low cost. Its session service gives us a durable log, but it will not build the prompt, hold workflow truth or make approval decisions.

ADK owns

  • Inner loop: Model call, tool call, tool response.
  • Tool schemas: Generated from Python functions.
  • Transcript: DatabaseSessionService on PostgreSQL.
  • Model swap: BaseLlm lets evals use a scripted model.
  • Model-call cap: RunConfig.max_llm_calls.

We own

  • Workflow state: State machine in errand.
  • Approvals: Hash-bound records, single use.
  • Side effects: Saga, idempotency, recovery.
  • Prompt content: ContextAssembler replaces ADK's history.
  • Memory and trace: Provenance, forgetting, cost, context log.

What I tested

The session, collision and rotation rows ran on PostgreSQL. The others ran on SQLite, or against live Gemini.

QuestionResultEffect on the design
Can evals run offline?YesA BaseLlm subclass ran a scripted tool call, tool response and final text with no network.
Does a session survive restart?YesA new service object on the same database read back all 4 events.
Can we control what the model sees?Yesbefore_model_callback replaced the contents. The model saw only our text, and a test secret in the user message did not reach it. Budget and forgetting rely on this.
Is the model-call limit enforced?YesIt raises LlmCallsLimitExceededError. The controller must catch this and turn it into a clear reply.
What if the model invents a tool?SafeA made-up book call ran nothing. ADK fires on_tool_error_callback, so we route that to the gateway. The gateway logs it, counts it and returns the error. The model receives the error, and it is saved in the session.
Can two writers share a session?NoWhoever holds the older copy gets StaleSessionError. A background write during a tool call killed the user's run. With no lock, two turns at once also left one failed. So only api writes to ADK sessions, under the turn lock.
Does forgetting really remove text?Yesdelete_session removed all 4 event rows, including the one holding a test secret. This supports rotating the session on forget.
Are live calls bounded by default?Nogemini-3.8-flash held each call until our timeout (504 at 18.7 s with a 20 s limit, 98.9 s with a 100 s limit). The lite model never failed, but 5 of 12 calls took over 5 s. We need a request timeout and an outer deadline, and the brief requires hard limits anyway.

ADK features we will not use

  • require_confirmation: It carries a confirmed flag, not a binding to provider, slot and price.
  • Resumability: Its docs say best effort and at-least-once. That is unsafe around book.
  • Events compaction: Marked experimental and LLM-based. We need deterministic context that tests can prove.
  • Session state for workflow: It lives in another database, so it cannot share a transaction with approvals.
  • Workflow graphs: They would add a second state model.

Costs to manage

  • Forgetting: The ADK transcript is append-only, so it keeps forgotten text. We send the model a redacted turn_view and rotate the ADK session on forget, which deletes the old rows.
  • Table creation: ADK manages its own tables, so it has its own database and Alembic stays out of it.
  • Dependencies: ADK and its dependencies install about 68 packages. It needs Python 3.11 or later. The image pins the versions.

Core flows

Workflow state machine

  1. INTAKE
  2. SEARCHING
  3. COMPARING
  4. AWAITING_APPROVAL
  5. EXECUTING
  6. VERIFYING
  7. DONE
  • Other states: DISRUPTED (provider cancelled, re-enters COMPARING), FAILED and LIMIT_REACHED.
  • Control: A transition table in code rejects illegal moves, and a version column stops two processes from overwriting each other. The model cannot set state.
  • Run outcomes: Every run ends as done, needs_input, awaiting_approval, verifying, limit_reached or tool_failed. Each one has a user-facing reply.

Approval and booking

  1. ModelCalls propose_booking(provider_id, slot).
  2. CodeCalls hold_slot and reads the quoted price. If it differs from the search price or breaks the budget, the card says so.
  3. CodeWrites an approval row with action, user, provider, slot, price, hold ID, expiry and a SHA-256 hash of those fields. The card is built from these fields only, never from model text or reviews.
  4. UserClicks Confirm, or types a whole-message match such as "yes" or "book it". The controller checks this before the model runs. "Yes, but Saturday" is not a match, so it goes to the model as a change.
  5. CodeCommits one transaction: conditional update of the approval to consumed, attempt row with key book:<approval_id>, outbox row. The user sees "booking in progress, not confirmed yet".
  6. WorkerClaims the attempt. The gateway recomputes the hash from current data and refuses on any mismatch. It then calls book.
  7. WorkerAlways calls get_booking_status. Only a verified booking creates the success notification, and its text is a template. SSE delivers it to the chat.
Book resultStatus checkAction
successbookedNotify with verified details.
slot_takennot bookedClose this approval. Show other slots. Any new choice needs a fresh approval.
timeoutbookedDo not retry. Notify with verified details.
timeoutnot bookedRetry with the same hold and same key, at most twice.
hold_expirednot bookedTake a new hold and ask for a fresh approval, even if the price is the same.
Any, or worker diedstatus unavailableAttempt stays open. The user sees "not confirmed yet". The sweep re-queues it after the lease expires.

Prompt injection defence

  • No power to abuse: The model has no side-effect tool, and approval comes only from the raw user message or a click.
  • Labelled data: Reviews reach the model as JSON fields marked untrusted. The gateway flags suspicious text in the trace.
  • Clean card: Provider free text never appears on the approval card.
  • Memory provenance: A memory is explicit only if its quote appears verbatim in a user message. Text from a review can never pass this check.
  • Remaining risk: A review can still bias a recommendation. The user sees exact details before approving, and code enforces hard limits on budget and time.

Context assembly (8,000 estimated tokens)

  • Counted: System prompt and tool declarations count against the budget.
  • Filter first: SQL keeps only rows that are active, not superseded, and either explicit or user-confirmed.
  • Then rank: Deterministic score on service and scope, with no embeddings. This stays reproducible offline.
  • Trim order: Older turns, then summary, then memories. Current request and current tool calls stay. Large tool results shrink first.
  • Worker events: Notifications from errand enter here on the next turn, so the worker never touches an ADK session.
  • Counting: Offline uses a pessimistic chars / 3 estimate. Live runs log the real count beside it.

Your decisions

PostgreSQL, Redis and Docker Compose are settled. Three calls on this list follow from them, so I made them. Tell me if you disagree.

DecisionMy recommendationAlternative and cost
Where does the saga run? NewIn worker. An API restart cannot interrupt a booking, and api stays free to scale. The reply arrives through SSE.Run it inside the approval request. The reply is simpler, but restart safety then rests entirely on sweeps.
